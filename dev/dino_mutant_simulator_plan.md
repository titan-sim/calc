# 다이노 뮤턴트 시뮬레이터 — 설계 정리

> 앞으로 작업하면서 계속 참고할 기획 문서. 새 내용이 정해지면 이 파일에 계속 업데이트할 것.

## 1. 프로젝트 개요

다이노 뮤턴트(모바일 게임)에서 공룡을 실제로 싸우게 하기 전에, 웹 시뮬레이터로 미리 결과를 예측하는 도구.

- 타이탄(보스) 공략 예측
- 공룡 대 공룡 대전 예측
- 아레나(5:5, 전열 2 / 후열 3) 예측
- (향후) 로그인 + 다른 유저와 실시간 대전

## 3. 스탯 계산 공식 (확정)

기본 계산은 룬 정수/퍼센트 바구니 + 별자리(정수) + 알 스킨·둥지(퍼센트) + VIP(11~13 레벨만 퍼센트)가 **같은 바구니에 합산**됨:

```
최종 공격력 = (기본공격력 + 룬 정수합 + 별자리 정수)
              × (1 + (룬 퍼센트합 + 알스킨% + 둥지% + VIP%) / 100)

최종 체력   = (기본체력 + 룬 정수합 + 별자리 정수)
              × (1 + (룬 퍼센트합 + 알스킨% + 둥지%) / 100)
```

**치명타 확률/피해**: 별자리도 룬과 동일하게 그냥 더함 (기본 치확 3% / 치피 105%에 가산).

**예외: 보스 슬레이어는 곱연산 증폭 레이어** — 유일하게 위 퍼센트 바구니에 들어가지 않는 룬. "타이탄과 싸울 때만" 아래처럼 최종 공격력에 한 번 더 곱해짐 (`js/core/stat-calc.js`의 `getTitanCombatMetrics`, `js/core/simulation-titan.js`에서만 적용됨 — 일반 `getBattleStats`/내 공룡 요약에는 영향 없음, 보스 상대가 아니면 이 룬은 비활성이라는 게임 내 설명과 일치):

```
증폭 전 최종 공격력 = 위 공식 그대로
증폭 후 최종 공격력 = 증폭 전 최종 공격력 × (1 + 보스 슬레이어%)
```

**검증된 예시**
- 공격력: (878 + 125) × 1.52 = 1524
- 체력: (7810 + 180) × 1.25 = 9987
- 레벨(내 공룡 요약바) = 기본 공격력 + floor(기본 체력 / 10) + 이동속도 → 예: 공격력 886, 체력 7810, 이동속도 150 → 886 + 781 + 150 = **1817**

## 4. 룬 시스템

- 정수 바구니(`atk_f`, `hp_f`)와 퍼센트 바구니(`atk_p`, `hp_p`)로 룬 수치를 합산 후 최종 공식에 대입
- **흡혈 룬 예외 처리**: `VAMP_EXCLUSION_LIST = ["고독한 분노", "협동 공격", "마지막 선물", "보스 슬레이어"]` — 이 룬들이 주는 공격력 보너스는 일반 전투 데미지 계산에는 포함되지만, 흡혈량 계산용 "기준 공격력"에서는 제외됨 (오버밸런스 방지용 설계)
- 조건부 발동 룬: 협동 공격(5마리 이상), 고독한 분노(1마리), 낙뢰/메테오(확률 폭딜), 트리플 임팩트(3타마다), 보호막(피격 감소), 힐/희생/죽을 준비/마지막 선물(피격·사망 시 트리거)
- `압축된 힘` / `매머드의 힘`은 상호 배타적 장착
- `UNSUITABLE_RUNE_LIST`: 컨텍스트별(현재는 타이탄) 부적합 룬 — 룬 목록 하단에 흐리게 별도 표시. `createRuneUI({ unsuitableList, unsuitableLabel })`로 페이지마다 다른 목록 주입 가능 (아레나/공룡 대전용 목록은 아직 미정, 필요 시 추가)
- 룬은 총 39개, 정렬 기준은 **등급(일반→희귀→에픽→유니크→전설) → 같은 등급 내에서는 이미지 파일 번호(`RuneSprite_N`) 오름차순**

**룬을 성격별로 분류하면 (타이탄 "관련 수치" 계산의 기준)**:
| 분류 | 룬 | 계산 방식 |
|---|---|---|
| 스킬 대미지 | 트리플 임팩트(일반, 3타마다 확정 발동=공격당 평균 1/3), 낙뢰/메테오(전설, 확률 발동) | 최종 공격력 × burst_p% × 발동확률(빈도) × 치확치피 평균배율 |
| 대미지 감소(확정) | 단단한 피부 1/2, 타이탄 가드(신규, 에픽) | red_f 그대로 합산 |
| 대미지 감소(확률) | 피해 저항 1/2 | red_f × prob% 기댓값 합산 |
| 회복 | 힐(피격 시 확률로 체력%), 흡혈(공격 시 확률로 공격력%) | 각각 prob% × 회복량 기댓값 |
| 공격력 증폭(곱연산) | 보스 슬레이어(유니크) | 위 3번 항목 참고 |

**신규 룬 — 타이탄 가드** (에픽, `RuneSprite_39`): "보스에게 공격당할 때 피해 {red_f}만큼 감소". 단단한 피부와 동일하게 확정 감소형이라 시뮬레이션/관련 수치 계산 양쪽에 반영됨.

**낙뢰/메테오 21레벨 이상 추가 효과** (실제 인게임 툴팁 기준으로 수치 보정 완료):
- 낙뢰: `insta_hp`(상대 체력 몇 % 미만) / `insta_prob`(즉사 확률) — 즉사 로직 자체는 아직 시뮬레이션에 미연결
- 메테오: `area_burst_p`(주변 타일 추가 피해%) — 아레나 등 다중 타일 전투에서 쓸 예정, 타이탄전(1타일)엔 미연결
- `desc`가 레벨에 따라 문구가 달라져야 해서 문자열 대신 **레벨을 받는 함수**로 정의 가능하도록 `resolveDesc()` 헬퍼로 처리 (`js/ui/rune-ui.js`)

## 5. VIP 시스템

- VIP 0(없음)~13, 드롭다운은 `<select>`가 아니라 **커스텀 드롭다운**(이미지+텍스트 표시 필요해서). 배지 이미지 `assets/vip/Vip_Setting_Icon0~3.png` (0~4/5~7/8~10/11~13 구간별로 다른 이미지), 이미지 위에 VIP 레벨 숫자를 흰 글씨로 중앙 오버레이
- 공룡 수: VIP 없음=5마리, 1~7=6, 8~10=7, 11~12=8, 13=9마리(VIP 자동 설정, `vipToDinoCount()`). 수동 드롭다운 상한은 9였다가, 인게임 공룡 수 증가 패키지 출시(2026-09-03)로 13까지로 확장됨(VIP 자체 최대치와는 별개) - `js/pages/my-dino-page.js`
- 설명 텍스트: 1~7 "부족 유닛: +1" / 8~10 "+2" / 11 "+3, 공·체 +3%" / 12 "+3, 공·체 +6%" / 13 "+3, 공·체 +9%"
- **11~13의 공·체 %는 룬/둥지·알스킨과 같은 퍼센트 바구니에 합산** (`getEffectiveBonusPercent()` — 내 공룡 페이지 어디서든 이 함수를 거쳐서 최종 % 계산)

## 6. 데이터 저장소 설계 (localStorage, 키: `dino_my_profile`)

내 공룡 프로필 하나에 전부 저장:
- `baseAtk`(기본1) / `baseHp`(기본10) / `moveSpeed`(기본100, 1~150 범위) / `vip`(기본0) / `dinoCount`
- `constellation`: 체력/공격력/치확/치피/건축물피해증가/스튜효과증가/이동속도/보스피해감소/보스피해증가 (전부 기본 0, 건축물·보스피해 계열은 정수, 나머지 %는 소수 가능)

- `runePresets`: **9개 고정 슬롯**, 각각 `{ name, runes(5슬롯) }`. 프리셋 삭제 기능은 없음(대신 슬롯을 비우면 됨). 버튼 이미지는 `assets/rune preset/PresetBtn.png`(비활성) / `PresetBtn_Select.png`+`PresetBtn_Select0~7.png`(9개 프리셋 각각 활성색 다름)

## 7. 타이탄 페이지 구성

1. **내 공룡** — `my-dino-page.js` 임베드 (레벨/공격력/체력/치확치피/공룡수 요약바 + 기본스탯/별자리/둥지알스킨/룬조합 탭)
2. **관련 수치** — 신규 카드. 2×3 타일 그리드(전부 같은 크기):
   - 평타 대미지 / 스킬 대미지
   - 공격력 증폭량 / 최종 평균 대미지 (=평타+스킬)
   - 대미지 감소량 / 회복량

   각 타일 클릭 시 아래에 그 항목에 관여한 개별 룬 계산값이 펼쳐짐 (`getTitanCombatMetrics()` 결과 기반, `js/pages/titan-page.js`의 `renderMetricDetail()`). 값이 0(기본값, 관련 룬 미장착)이면 흰 글씨, 0이 아니면(변화가 생기면) 노란 글씨로 자동 강조(`.value-changed` 클래스).
3. **전투 설정** — 타이탄 레벨(1~120) / 전투 제한시간 드롭다운 + 타이탄과의 거리(타일) / 연속 전투 토글. 거리·연속전투 모두 `simulation-titan.js`에 연결됨: 연속 전투 켜짐 시 사망한 공룡이 1.5초 + (거리 × 타일당 이동시간) 후 재소환되어 다시 합류.
4. **시뮬레이션 시작** 버튼 → `runTitanSimulation()` 500회 반복
5. **시뮬레이션 결과** — 총 피해량/남은 체력/평균 시간/사망 수 + 시간대별 체력 변화 그래프 + (설정에서 상세 로그 켰으면) 로그 다운로드

**타이탄 레벨 데이터 (`js/data/titan-data.js`, 1~120레벨)**:
- 1~50레벨: 기존 검증된 값 그대로
- 51~120레벨: 51레벨 +18,750,000 티어 가중치, 이후 매 레벨 +5,000,000 누적. **32비트 float(Math.fround) 반올림 오차까지 재현**해서 실제 인게임 표기(58/60레벨 끝자리 8, 100/114/120레벨 끝자리 24 등)와 정확히 일치하도록 구현함. 50레벨 이론값(181,875,000)을 Float32로 변환한 181,875,008을 시작점으로 씀
- 공격력은 별도 연구 자료 없어서 기존 선형 공식(레벨당 +15) 그대로 120레벨까지 연장

## 8. UI/디자인 컨벤션 (중요 — 새 UI 만들 때 반드시 따를 것)

- **드롭다운은 항상 커스텀 드롭다운으로 통일**. 네이티브 `<select>` 금지 (안 예뻐 보인다는 피드백). 패턴: `<div class="custom-dropdown"><div class="selected-value">...</div><ul class="dropdown-list">...</ul></div>`. 열기/닫기는 `selectedValue.onclick`에서 다른 모든 `.dropdown-list` 닫고 자기 것만 토글. 바깥 클릭 시 전체 닫힘은 `initMyDinoPage`/`initTitanPage`에 있는 공용 `document.addEventListener("click", ...)` 하나가 `.dropdown-list` 전체를 관리(중복 등록 주의). 아이콘이 필요한 드롭다운(VIP)은 `<li>` 안에 이미지+텍스트 자유롭게 구성 가능하다는 게 커스텀 드롭다운을 쓰는 이유.
- **입력칸/드롭다운 높이는 반드시 통일**: `input, select, .selected-value` 전부 같은 `height`/`padding` 규칙 공유. 이미지가 들어가는 특수 드롭다운(VIP)도 트리거 박스 높이는 절대 벗어나지 않게 이미지 크기를 맞춤.
- **반응형은 카드 폭 비례 스케일링(cqw) 사용, 미디어쿼리 브레이크포인트 아님**. `.card { container-type: inline-size; }`이 이미 걸려있어서 카드 내부 요소는 `clamp(최소px, Xcqw, PC기준px)` 형태로 작성하면 카드 폭이 줄어드는 만큼 높이/패딩/폰트가 전부 비례해서 같이 줄어듦 (모바일에서 "세로로 뚱뚱해지는" 현상 방지). X는 `(PC기준px / 600) × 100`으로 계산(600=`--container-max` 기준). 새 UI 요소를 추가할 때도 고정 px 대신 이 패턴을 써야 함.
- **기본값 대비 변경 강조**: `.value-changed` 클래스 = `color: var(--accent) !important` (다른 동일 특이도 클래스보다 소스 순서상 앞에 있어서 `!important` 필요했음). 입력값이 기본값이면 흰색, 바뀌면 노란색. 새 입력 필드를 추가할 때마다 초기 렌더링 시점 + blur/change 시점 둘 다에서 `markChanged(el, value !== 기본값)` 호출 필요.
- **카드 안 여러 룬이 계산에 관여하는 수치는 클릭하면 개별 breakdown이 펼쳐지는 패턴** (관련 수치 카드 참고) — 앞으로 비슷한 집계값(예: 아레나 전열/후열 대미지 등)에도 재사용 가능.
- 이모지 아이콘은 카드 제목(h2)이나 설정 행에 쓰지 않기로 함(전투 설정 카드에서 ⚙️📏🔁 다 제거함) — 텍스트만으로 충분히 깔끔한 디자인 지향.
- `.dino-panel`에는 `overflow: hidden`을 쓰면 안 됨 — 내부 드롭다운 팝업이 카드 경계에서 잘림. 모서리 둥글게 처리가 필요하면 해당 자식 요소(`.dino-summary-bar` 등)에 개별 `border-radius`를 주는 걸로 대체.

`initHomeTileTilt()`(`js/pages/home.js`) + `.home-tile-main`(`css/home.css`)을 여러 차례
다시 만들었던 과정 기록:
1. rotateX/rotateY + 은은한 radial 반사 스팟 + 대각선 빛 띠(`.home-tile-glare`, `--shine-angle`) →

2. 테두리를 커서 위치(`--glare-x/y`) 따라가는 radial-gradient border로 구현(border-box 배경
   레이어 트릭) → "커서 따라다니는 노란 불빛 없애라"는 요청으로 폐기, 테두리는 다시 고정

3. box-shadow 여러 겹으로 "두께감" 흉내 → "같잖은 짓, 진짜 3D로 만들어라" 피드백으로 폐기.
4. `perspective(420px)` + `transform-style:preserve-3d` + 실제 옆면 4개(90도로 접어 붙이는
   "CSS 큐브" 방식, 두께 `--thickness:12px`)로 진짜 지오메트리 두께를 시도. Playwright
   스크린샷/transform 값 자체는 그럴듯해 보였지만 사용자가 실제 화면에서 "안 된다"고 판단 -
   원인 불명으로 재작업 보류.
5. **원인 규명 + 최종 구현(완료).** 재조사 결과 실제 버그를 특정함: `.home-tile`의 등장
   애니메이션(`animation:...forwards`)이 `opacity`와 `transform`을 한 애니메이션에 같이
   태웠는데, `forwards` fill-mode 때문에 애니메이션이 끝난 뒤에도 CSS 우선순위상 애니메이션이
   인라인 스타일보다 위라 JS가 넣는 `transform`을 계속 무시하고 있었음(`getComputedStyle`로
   확인하면 항상 `matrix(1,0,0,1,0,0)`=무회전) - opacity 애니메이션과 transform 애니메이션을
   분리(`home-tile-fade-in`엔 forwards 유지, `home-tile-slide-in`엔 forwards 제거)해서 해결.
   이게 4차 시도까지 "코드는 맞아 보이는데 화면에서 안 보인다"고 느껴졌던 진짜 원인이었음.
   추가로, 4차의 옆면(엣지) 지오메트리도 실측(`getBoundingClientRect`)해보니 회전각을 60도까지
   줘도 옆면 투영 폭이 정확히 0px로 나오는 별개의 렌더링 버그가 있어서(3D 중첩 합성 문제로
   추정) 포기하고, 기울어진 방향의 모서리에 그라데이션이 몰리는 2D 인셋 글로우

합집합으로 넓혀 문제 (2)를 구조적으로 해결함. 부수적으로 `runTitanSimulation`에 `onProgress` 없이
호출될 때 반복마다 `setTimeout(0)`으로 쪼개지던 타이머 오버헤드를 줄이기 위해 opt-in `batchSize`
파라미터를 추가하고 2단계 정밀 계산 호출에 `batchSize:10` 적용(실전 시뮬레이션 버튼은 진행률 표시를
위해 기본값 1 그대로 유지, 무변경). 균형 조합의 기하평균 공식 자체는 이미 수학적으로 올바름을
재확인해 변경하지 않음. Node 스크립트(랭킹 상관관계 + 반복 안정성)와 Playwright E2E로 검증 완료.

**추가 버그 수정(같은 묶음, 후속 리포트로 발견):** 적합 룬을 2개만 빼고 거의 다 보유한 상태로
"조합 찾기 시작"을 누르면 아무 반응이 없다는 리포트가 들어옴. 원인은 위에서 추가한
`Math.max(...screened.map(...))`(전체 조합의 해석적 균형 점수 정규화용) — `screened` 배열이
보유 룬 개수에 따라 수만~수십만 개(예: 적합 룬 32개 중 30개 보유 시 C(30,5)=142,506개)까지 커질 수
있는데, 스프레드 연산자로 함수 인자에 통째로 펼치면 V8 인자 스택 한도(약 6만5천개)를 넘겨
`RangeError: Maximum call stack size exceeded`가 터짐. `async` 함수 안에서 try/catch 없이 터진
동기 예외라 처리되지 않은 Promise 거부로 조용히 죽어서, 버튼이 비활성 상태로 멈춘 채 아무 것도
안 바뀌는 것처럼 보였음. `Math.max(...array)`를 `array.reduce((m,v)=>Math.max(m,v),0)`로 교체해서
배열 크기와 무관하게 안전하게 고침(`refined`를 대상으로 하는 다른 두 `Math.max(...)` 호출은 후보군
크기가 최대 90개로 고정돼 있어 안전, 무변경). Playwright로 같은 시나리오(적합 룬 32개 중 30개
보유) 재현 후 정상 동작 확인.

**추가 개선(같은 묶음, 후속 리포트로 발견): 조합 찾기 결과가 같은 입력으로도 실행마다 조금씩
달라짐.** 1단계(해석적 계산)는 완전히 결정론적이라 후보군 자체는 항상 동일하지만, 2단계는 각
후보를 `runTitanSimulation`으로 30회 실제 시뮬레이션(치명타/발동 룬 확률 롤 등 `Math.random()`
사용)해서 평균 내는 구조라, 진짜 생존 시간이 근소하게 갈리는 조합끼리는 그 30회 표본이 매 클릭마다
새로 뽑히면서 "생존 시간 최고"/"균형 조합"의 승자가 실행마다 뒤집힐 수 있었음(1마리 로스터처럼
분산이 큰 시나리오에서 5회 반복 재현 시 실제로 승자가 바뀌는 것을 확인).

첫 시도로 시드 고정 PRNG(`Math.random`을 입력 기반 시드로 임시 교체)를 추가했었으나, 사용자가
"그건 운 나쁜/좋은 30회를 매번 똑같이 재현할 뿐 진짜 값에 더 가까워지는 게 아니다"고 정확히
지적해서 **폐기**하고 대신 3단계 구조로 바꿈: 1단계(해석적, 전체 조합) → 2단계(30회, 후보
~90개) → **3단계(신설, 200회) — 2단계 결과 상위권(생존 시간 상위
`TITAN_OPTIMIZER_VERIFY_TOP_N`(=10)개 + 균형 점수 상위 10개 + 대미지 최고 조합, 중복 제거해서
보통 15~20개)만 추려 훨씬 높은 회차(`TITAN_OPTIMIZER_VERIFY_ITERATIONS`=200)로 다시 시뮬레이션해서
그 결과로 최종 승자를 정함**. 표본을 30→200으로 늘려 평균이 진짜 기댓값에 더 가까워지게 하는
방식이라 시드 방식과 달리 "틀린 답을 재현 가능하게" 만드는 게 아니라 실제로 더 정확해짐.

검증 결과(Node, 이전에 승자가 계속 뒤집혔던 1마리 로스터 고분산 시나리오 5회 반복): "생존 시간
최고 조합"은 승자와 예상 생존 시간 값(0.15초 편차, 이전엔 0.8초+승자 자체가 바뀜) 둘 다 안정화됨.
"균형 조합"만 두 조합 사이에서 여전히 가끔 갈렸는데, 200회와 2000회로 각각 정밀 비교해보니
두 조합의 실제가 기댓값(DPS는 애초에 정확한 값, 생존 시간은 200회나 2000회나 거의 같은 값으로
수렴)이 이미 수렴해 있었고, 두 조합이 "DPS ~3.3% 낮은 대신 생존 시간 ~3.3% 높음"이라는 거의
대칭적인 트레이드오프 관계라 균형 점수(기하평균) 자체가 진짜로 근소하게 동률인 상황이었음 —
표본 부족으로 인한 착시가 아니라 실제로 우열을 가리기 어려운 두 선택지라는 뜻. Playwright
브라우저 검증에서는 3회 반복 모두 결과가 완전히 동일했음(다만 이 근소 동률 케이스는 시나리오에
따라 여전히 나타날 수 있음 - 위 이유로 정상적인 현상). 후보 수가 많고 오래 버티는 빌드에서는
3단계 추가로 총 소요 시간이 다소 늘어남(예: 조합 12개 기준 이전 ~8초 → ~22초 — 정확도를 위해
받아들인 트레이드오프).

정확히 같은 값(`timeLimitSec`)으로 동점 처리되는 것 — 1단계(해석적 스크리닝)에서 동점 그룹 안의
순위가 사실상 조합 배열 순서에 좌우되는 무작위 추첨이 되어버려서, 더 안전한 단단한 피부 2 조합이
운 나쁘게 상위 30위 후보에서 빠지고 피해 저항 2 조합만 2단계로 넘어가는 일이 생김.

`js/core/stat-calc.js`의 `estimateTitanSurvivalSec()`을 수정 — `netDrainPerSec <= 0`일 때도
단순히 `timeLimitSec`을 리턴하지 않고, 마진(`-netDrainPerSec`)이 클수록(더 안전할수록) 점수가
높아지도록 `timeLimitSec + finalHp / max(1, -netDrainPerSec)`를 리턴해서 동점 그룹 안에서도
순위가 갈리게 함. 확정형 감소가 확률형 감소보다 항상 기댓값이 높거나 같으므로(마진도 항상
크거나 같음) 이 방식이면 항상 올바른 방향(확정형 우선)으로 줄을 세움 — 회복의 분산·상한
클리핑까지 완전히 반영한 확률적 생존 모델은 훨씬 복잡해서(사실상 반사 경계가 있는 확률보행의
초회 통과 시간 분포를 구해야 함) 이번엔 손대지 않고, 방향성만 정확한 마진 기반 타이브레이킹으로
실용적으로 해결함 - 완전한 모델이 필요해지면 그때 다시 검토.

검증: 사용자가 리포트한 것과 같은 조합(단단한 피부 2·피해 저항 2 둘 다 Lv31 보유)을 Node와
Playwright 브라우저 양쪽에서 재현 — 수정 전에는 2단계 표본이 우연히 좋게 나온 피해 저항 2가
균형 점수에서 단단한 피부 2를 앞서는 경우까지 있었지만(3단계 정밀 재검증이 이를 바로잡음),
수정 후에는 "생존 시간 최고"/"균형 조합" 둘 다 일관되게 단단한 피부 2를 선택함, 피해 저항 2는
어느 쪽에도 나오지 않음.

0이 되는 순간)의 로그가 한 번도 안 남고 그 직전 틱에서 기록이 끝나버렸음(실제 시뮬레이션 계산
자체는 항상 정확히 0까지 갔음 - 화면에 보여주는 리플레이 로그만 마지막 틱을 빠뜨렸던 것). 사용자의
"여러 명이 동시에 공격해서 생기는 버그 같다"는 추측은 정확한 메커니즘은 아니었지만 증상 관찰은
정확했음. `titanDefeated` 플래그를 도입해서, 죽음을 감지하면 즉시 break하는 대신 "그 틱의 로그
기록까지는 마치고" break하도록 순서를 바꿈(타이탄이 이미 죽었으면 그 틱에 반격은 안 하도록
`t%3===0` 블록에 `!titanDefeated` 가드 추가). Node로 마지막 로그 항목이 정확히 0인 것, Playwright로
실제 리플레이 화면이 체력 0%/"0 / 2,500,000"까지 도달하는 것 확인.

**(b) [중요] 조합 찾기 정확도 회귀 버그 — `estimateTitanSurvivalSec`의 finalHp 무한대 확대.**
사용자 리포트: 타이탄 레벨 1에서 흡혈 하나만 넣어도 안 죽는데, "생존 시간 최고 조합"엔 흡혈이
아예 안 들어가고 방어벽+매머드의 힘+체력증가3(Lv1)+협동+체력증가2(Lv1)(전부 방어/회복 능력 0,
순수 체력빨) 조합이 뽑힘 - 원인: 이 함수가 "제한 시간까지 버티는" 경우를 `finalHp/소모율`로
계산하는데, 소모율(소모 - 회복)이 0에 아주 가까운 양수일 때(방어 룬이 하나도 없어도 상대가
극도로 약해서) 이 값이 나눗셈 때문에 무한정 커짐 - 순수 체력빨만 큰 조합이 실제 안전 마진과
무관하게 점수가 수십 배로 부풀려져서, 진짜 안전한(회복/완화형) 조합을 밀어냄. 직접 수치 재현으로
확정(구버전 점수: 방어형 콤보 20,158 vs 흡혈 콤보 2,297 - 버그 그대로 재현됨). "제한 시간에 정확히
맞춰 죽으려면 초당 얼마나 깎여야 하는지"(`finalHp/timeLimitSec`)를 기준선 삼아 실제 소모율이
거기서 얼마나 낮은지를 마진으로 쓰도록 공식을 다시 씀 - finalHp가 나눗셈 분모가 아니라 고정된
timeLimitSec으로 나눈 값이 분자 쪽에 들어가므로 체력을 아무리 불려도 무한정 커지지 않음(신버전
점수: 흡혈 콤보 2,301 vs 방어형 콤보 1,817 - 정상적으로 역전됨). 묶음 11에서 고친 단단한 피부
vs 피해 저항 케이스도 회귀 없이 여전히 올바른 순서인 것 재확인. 사용자가 리포트한 것과 동일한

   조합"보다 낮게 나올 수 있었음.
2. **1단계 안전망(`deterministicReduction`, 묶음 13/14)이 확정 대미지 감소 룬(단단한 피부 등)만

   기대지 않아도 최소 이 정도는 버틴다"는 안전망 취지에 안 맞았음.

  `survivalRate`(0~1)를 결과 객체에 새로 추가(시뮬레이션 호출 자체는 늘지 않음 - 이미 계산 중이던
  값을 하나 더 집계할 뿐이라 속도 영향 없음).
- `titan-page.js`: 1단계 안전망을 `deterministicReduction`(합산값) 대신
  `deterministicSurvivalEstimate`(= `finalHp / (확정 감소만 반영한 소모율)`)로 교체 - `finalHp`에
  이미 방어벽 등 체력% 룬 효과가 반영돼 있어서 확정 감소와 확정 체력 증가를 하나의 지표로 함께
  평가함. 2단계(`refined`)·3단계(`verified`) 모두 `survivalRate`를 실측값으로 같이 들고 다니게
  하고, "생존 시간 최고" 최종 선정과 균형 점수 계산 둘 다 `survivalRate`를 1순위 기준으로 바꿈
  (동률이면 기존처럼 평균 생존 시간 -> DPS 순으로 타이브레이크). 균형 점수 공식도
  `sqrt((dps/maxDps) * survivalRate)`로 교체(이미 0~1이라 별도 정규화 불필요, 기존 "평균 생존
  시간을 최댓값 기준 정규화"보다 훨씬 정직한 지표). 결과 화면에도 "생존율(한 마리도 안 죽을 확률)"
  카드를 새로 추가해서 추천 근거가 눈에 보이게 함.

**검증:** (1) Node로 위 표의 실측 사망률 재현(150회씩 개별 시행 - `avgTimeSec`가
`timeLimitSec` 미만이면 그 시행에서 죽은 것으로 판정하는 방식으로 직접 셈). (2) 수정 후 실제

조합" 모두 방어벽·타이탄 가드가 포함된 조합으로 바뀌고 셋 다 "생존율 100.0%"로 표시됨(수정 전
버그 조합은 더 이상 선택되지 않음). (3) 묶음 16에서 검증했던 타이탄 레벨 1(타이탄이 공룡보다

### ✅ 완료 — 묶음 18: 조합 찾기를 연속 전투(무한 재소환) 기준으로 재정의 + 오버힐 반영 1단계 재작성

사용자가 흡혈의 **오버힐**(체력이 이미 최대치면 흡혈이 낭비됨) 문제를 지적하면서 재검토가 시작됐고,
논의 중 더 근본적인 문제가 드러남: 조합 찾기가 애초에 `continuousBattle`(연속 전투 - 공룡이 죽어도
1.5초+이동시간 뒤 무한 재소환, 재소환 횟수 제한 없음 - `simulation-titan.js` 확인)이 켜져 있으면
"공룡 한 마리라도 죽으면 실패"라는 지난 묶음(17)의 전제 자체가 성립하지 않는다는 것.

**사용자와 논의해서 확정한 방향:**
1. 조합 찾기는 전역 설정과 무관하게 항상 `continuousBattle:true` 기준으로 계산(조합 찾기 탭에
   "연속 전투 ON(조합 찾기 전용 고정)" 요약표를 새로 추가해서 명시).
2. "생존"의 정의를 `survivalRate`(무사망 확률)에서 `avgDeadCount`(평균 사망/재소환 횟수) 기반으로
   전환: 생존 우선=`avgDeadCount` 최저, 균형 조합=`survivalQuality=1/(1+avgDeadCount)`를 DPS와
   기하평균(`sqrt((dps비율)*survivalQuality)`) - 임계값/퍼센트 없이 "다들 많이 죽는 상황이면 생존
   쪽으로, 다들 안 죽는 상황이면 딜 쪽으로" 자연스럽게 쏠리는 게 핵심(사용자가 우려한 "생존이 너무
   짧으면 그 %도 의미없다" 문제를 애초에 피함). 2·3단계는 `runTitanSimulation`이 이미 반환하는
   `avgDeadCount`를 그대로 쓰므로 시뮬레이션 추가 없이 바로 적용 가능.
3. 1단계(시뮬레이션 없는 해석적 스크리닝)도 오버힐을 정확히 반영해서 재작성 - 기존
   `estimateTitanSurvivalSec`(평균 net 소모율 기반)는 흡혈/힐 평균 회복량을 "항상 100% 유효"로
   계산해 회복량이 큰 조합의 점수를 부풀렸음(하필 "회복이 소모를 이기는" 안전한 조합일수록 체력
   캡 근처에 머무는 시간이 길어서 왜곡이 가장 클 때 가장 크게 틀림).

**새 1단계 모델 (`estimateTitanExpectedDeaths`, `js/core/stat-calc.js`):** 재생 이론(renewal
theory) - 공룡 한 마리가 만수 체력에서 시작해 처음 죽기까지 걸리는 평균 시간(MTTF)만 구하면
기대 사망 횟수(T) = T/(MTTF+respawnDelaySec). MTTF는 체력을 25개 구간으로 이산화한 흡수 마르코프
체인에서 "k사이클 후에도 살아있을 확률"을 앞으로 전파하며 총합을 누적하는 방식(E[T]=ΣP(T>k))으로
구하고, 감쇠 비율(λ)이 안정되면 남은 무한 꼬리를 등비급수로 근사(퀘이사이-정상 분포 수렴 - 마르코프
체인 스펙트럴 갭 덕분에 실제 MTTF 크기와 무관하게 보통 수십 사이클 안에 안정됨). 오버힐 반영의
핵심은 "사이클 안의 회복 총합을 먼저 만수 체력에 클램프한 뒤 피해를 빼고 0에 클램프"하는 순서를
절대 하나의 net delta로 뭉치지 않는 것.

**구현 중 발견·수정한 버그 2개** (둘 다 Node 벤치마크/정확성 검증 과정에서 발견 - 처음 구현한
"흡수까지 기대 스텝 수" 선형계를 Jacobi 반복으로 직접 푸는 방식은 반복마다 최대 +1씩만 늘 수 있어서
성능 예산(반복 20~40회) 안에서는 큰 MTTF(수백~수천 사이클)에 절대 도달 못 함 - "이미 압도적으로
안전하니 조기 종료" 조건도 그 자체가 반복 횟수에 막혀 있어 사실상 죽은 코드였고, 방어가 전무한
조합과 극도로 안전한 조합이 똑같은 값(반복 상한)으로 수렴해버려 전혀 구분이 안 됐음 - 그래서
"확률질량을 앞으로 전파 + 등비급수 꼬리 근사" 방식으로 전면 교체함):
1. **λ(감쇠 비율) "수렴" 오판** - 확정형(분기 1개)이거나 방어가 강한 조합은 아직 한 번도 안 죽어서
   λ가 그냥 항상 정확히 1인 것뿐인데, 이걸 "정상 감쇠 상태로 수렴했다"고 착각해서 조기 종료 -
   `sawDecay` 플래그로 "확률질량이 조금이라도 실제로 흡수된 적이 있는지"를 따로 추적하도록 수정.
2. **완전 사망 시 `sawDecay` 누락** - 확정형 조합이 정확히 어떤 사이클에 죽으면 확률질량이 통째로
   0으로 떨어지는데, 이 "이미 확실히 죽음" 조기 종료 분기가 `sawDecay=true`를 안 세팅해서 위 1번
   버그의 안전망(sawDecay가 false면 훨씬 넓은 상한까지 계속 찾아봄)에 오히려 걸려버림 - 그 분기에도
   `sawDecay=true` 추가.
   
   두 버그 다 "서로 다른 방어 수준의 조합들이 똑같은 상수값으로 수렴해버림"이라는 동일한 증상으로
   발견함(Node로 직접 여러 조합을 나란히 계산해서 비교하다가 발각 - 겉보기엔 그럴듯한 숫자가
   나와도 반드시 서로 다른 입력이 서로 다른 출력을 내는지 교차 검증해야 한다는 걸 재확인).

**성능 튜닝:** 첫 구현(B=50버킷, 반복상한 40)은 조합당 최악의 경우 거의 항상 상한까지 돌아서
15,504개 조합에 7.7초(청크당 최대 2.4초, UI 정지 유발) - 버그 수정 후에는 조기 종료가 정상
작동해서 같은 설정으로도 훨씬 빨라짐. 최종 값: B=25버킷, 기본 반복상한 30(감쇠 관측된 뒤),
미관측 시 확장상한 150(그 안에서도 안 죽으면 "매우 안전"으로 간주 - 다른 조합과의 상대 순위엔

**최종 성능(Node 벤치마크):** 적합 룬 20개(조합 15,504개) 731ms, 25개(53,130개) 2.48초, 30개

**진짜 원인 발견 (Node로 사용자의 정확한 보유 룬/레벨/타이탄 레벨/120분 제한을 그대로 재현해서

2. 원인을 끝까지 추적(`singleDinoMTTFCycles`의 λ 수렴 과정을 사이클 단위로 직접 출력해서 확인):

바꿔서 진동에 안 속게 함(비교 기준도 λ 자체의 절대오차가 아니라 감쇠율(1-λ)의 상대오차로 바꿈 -
λ는 항상 1에 아주 가까워서 절대오차 비교는 사실상 무의미했음). (2) 확장 탐색 상한을

막기 위해 추가) 조정과 겹쳐 있었음 - 이번 묶음에서 이 두 안전망도 그대로 유지.

**검증:** (1) Node로 문제의 정확한 조합 쌍을 재계산 - "방어 없는 고DPS 조합"이 이제 기대 사망

세로 스택(주 내용 + 선택적 서브라인)으로 바꾸고 `.metric-detail-row-main`/`.metric-detail-row-sub`
신설(서브라인 없는 기존 행은 시각적으로 그대로 동일). 검증: Node로 `rawDmg×triggerRate=avgDmg`,
`rawAmount×prob/100=avg` 항등식이 정확히 성립하는지 확인 + Playwright로 낙뢰/흡혈/피해 저항 2/
트리플 임팩트를 실제로 장착해 브라우저에서 "낙뢰 (40% 확률) / 원래 대미지 1", "피해 저항 2 (30%
확률) / 원래 감소량 70" 형태로 정확히 렌더링되는 것, 콘솔 에러 없는 것 확인.

**(b) 조합 찾기 1~3단계를 "실측치에 거의 오차 없는 계산식"으로 완전히 대체할 수 있는지 검토.**
사용자 질문에 대한 결론: **불가능**. 이유 셋: (1) 체력을 구간(버킷)으로 나눠 계산하는 1단계
해석 모델은 버킷 수를 늘려도 오차가 단조롭게 안 줄어듦(묶음21에서 이미 확인된 현상 - 25개→1.6회,
50개→67.9회, 200개→58.3회인데 실측은 72.2회로, 50개가 오히려 200개보다 더 정확했던 사례가 있음).
(2) 보호막처럼 "한 마리가 죽으면 다른 마리에 영향" 없는 룬은 그나마 반영 가능하지만, 희생/죽을
준비/마지막 선물처럼 공룡 개체 간 상호작용이 있는 룬은 "공룡 1마리 계산 후 마리수 곱하기"라는
현재 모델의 독립성 전제 자체를 깨서 닫힌 형태 공식으로 못 풂. (3) 사용자가 지적한 오버힐도 이미
1단계가 반영 중이라 이 자체가 새로운 오차 원인은 아님. 대신 (i) 이미 반영 가능한 범위였던 **보호막
룬**을 1단계 모델에 새로 반영하고, (ii) 3단계를 실측 시뮬레이션을 유지하면서 불필요한 500회
검증만 건너뛰는 **계층화**로 구조를 바꿔 체감 속도를 높이는 절충안으로 진행(사용자 승인).

**보호막 모델링** (`js/core/stat-calc.js`): 기존엔 `estimateTitanExpectedDeaths`의 마르코프 체인이
보호막을 아예 반영하지 않아서(0 취급), 보호막만 낀 조합과 방어 전무 조합이 해석적으로 완전히
동일하게 나왔음. 보호막(N사이클 동안 곱연산 % 감소)은 확률이 아니라 스폰/재소환 후 흐른 사이클
수만으로 결정되는 **확정 카운트다운**이라(`simulation-titan.js`의 `shieldSteps`와 동일), 별도
마르코프 상태 차원을 늘릴 필요 없이 "사이클 k가 지속 기간 안인지"만으로 미리 만들어둔 두 분기
세트(보호막 있음/없음)를 사이클마다 골라 쓰는 방식으로 구현(`buildTitanCycleBranches`가
`downBranchesShielded`/`downBranchesUnshielded`/`shieldTurns`를 반환, `singleDinoMTTFCycles`가
`k < shieldTurns`로 선택). 감소 적용 순서(타이탄 가드는 보호막 배율 "전", 단단한 피부/피해 저항은
"후" - `simulation-titan.js`의 실제 순서와 동일)도 맞춰 반영. 검증: 보호막 미장착 시엔 대수적으로
기존 공식과 완전히 동일함을 수식으로 확인(회귀 없음 보장) + Node로 "방어 전무 vs 보호막만"
비교에서 해석값(228.92 vs 244.47)과 실측값(240.00 vs 255.00, 5000회) 둘 다 보호막 쪽이 안전하다고
정확히 일치 + "보호막+타이탄가드"(순서상 유리) vs "보호막+단단한피부1"(순서상 불리, 동일
레벨감 아님을 감안해도 방향 일치) 둘 다 해석·실측이 같은 방향으로 나옴을 확인.

**3단계 계층화** (`js/pages/titan-page.js`): 기존엔 최종 후보(finalists, 보통 10개 안팎) 전부를
무조건 500회씩 검증해서 이게 전체 소요 시간의 대부분(묶음21 실측 90%)을 차지했음. 새로 추가한
`TITAN_OPTIMIZER_PRESCAN_ITERATIONS`(60회) 예비 검증 단계를 사이에 끼워넣어: 2단계가 이미
무사망으로 확정한 후보(기존 캡체크 지름길)는 그대로 재검증 생략하고, 나머지는 먼저 60회로
가볍게 재본 뒤 "생존 1등을 통계적으로 이길 가능성이 있는지"(묶음23에서 검증된 이항분포 기반
동률 판정 `titanDeathCountsStatisticallyTied`를 재사용/공용 함수로 추출) 또는 "대미지가 최댓값의
85%(`TITAN_OPTIMIZER_CONTENDER_DPS_RATIO`) 이상인지" 둘 중 하나라도 해당하면 500회로 승격시키고,
둘 다 아니면(이미 통계적으로 못 이긴다는 게 확인됨) 예비 표본을 그대로 최종값으로 씀 - 근사가
아니라 "이길 가능성이 없는 후보에 500회를 안 쓸 뿐"이라 정확도 손실은 없음(대미지 최댓값 조합은
정의상 항상 자기 자신이 85% 조건을 만족해 매번 500회로 승격되므로 "최대 대미지 조합" 표시값은
항상 정밀함). 검증: Node로 stage1·2를 한 번만 계산해 finalists를 고정한 뒤, 그 동일한
finalists에 대해 구버전(전부 500회)과 신버전(계층화)을 각각 3회씩 반복 실행 - "추천 조합"과
"최대 대미지 조합"은 6회 전부 완전히 동일한 조합으로 수렴, "최대 생존 조합"은 이미 사실상 동률인
후보들(사망률 0~0.1대) 사이에서 갈렸는데 이는 **구버전도 반복마다 마찬가지로 갈렸음**(묶음23에서
이미 인지한, 근소 동률 후보 간의 정상적인 몬테카를로 표본 노이즈이지 이번 변경으로 생긴 회귀가
아님) - 소요 반복 횟수는 5,800회→2,960회(약 1.96배 단축), 극단적으로 안 죽는 titan 레벨(상대가
너무 약해 전부 오래 버티는) 시나리오에서는 오히려 전원이 경합 후보라 예비검증 오버헤드만 붙어
약 11% 느려지는 것도 확인(계층화의 최악의 경우 - 그래도 정확도 저하는 없음, 방향성 그대로
사용자에게 트레이드오프로 안내 가능).

**(c) 조합 찾기 결과 카드 개편.** 기존 "가장 안 죽는 조합/시간당 대미지 최고 조합/균형 조합(생존·
대미지 둘 다 준수)" 3개 제목과 각기 다른 항목 구성을(사망 횟수+dps 뿐) 사용자 요청대로 **"최대
생존 조합"/"최대 대미지 조합"/"추천 조합"** 3개 제목으로 통일하고, 셋 다 똑같이 **룬 5개 · 평균
사망 시간 · 평균 사망 수 · 예상 초당 대미지 · 평균 대미지 합계** 5개 항목을 보여주도록 통일함
(`comboBoxHtml()` 헬퍼로 중복 제거). 이 과정에서 `refined`/`preResolved`/`verified` 객체에
`avgTimeSec`/`avgTotalDmg`를 새로 실어 날랐음(기존엔 `avgDeadCount`만 들고 다니고 나머지는 버려지고
있었음). 부수적으로, "예상 초당 대미지" 표시값을 기존 1단계 해석적 dps(시뮬레이션과 무관한 이론값,
그래서 "빠른 계산"으로 같은 조합을 실측하면 조금씩 달라 보였던 원인 중 하나였음)에서 **이 조합을
실제로 검증한 시뮬레이션 결과(평균 대미지 합계 ÷ 평균 사망 시간)로 유도**하도록 바꿈 - 화면에
같이 뜨는 "평균 대미지 합계"와 항상 같은 시뮬레이션에서 나온 값이라 서로 앞뒤가 안 맞을 일이
없어짐. 사용자가 마지막에 리포트한 "추천받은 조합을 빠른 계산으로 다시 돌리면 평균 사망/예상
대미지가 조금씩 다르다"는 문제는, 이제 결과 카드 자체가 그 조합의 실측치를 바로 보여주므로
빠른 계산으로 재확인할 필요가 없어져 자연히 해소됨(남는 차이가 있다면 그건 두 번의 독립적인
500회 몬테카를로 표본 간 정상적인 오차 - 묶음23에서 이미 0.002~0.008 수준으로 확인된 현상). 검증:
Playwright로 실제 조합 찾기를 실행해 3개 카드 제목·5개 항목이 요청한 그대로 렌더링되는 것, 대미지
합계/사망 시간/유도된 dps가 서로 산술적으로 일치하는 것, 콘솔 에러 없는 것 확인.

### ✅ 완료 — 묶음 35: 모드 A 정밀도 상향(사전 필터링 기준·1단계 시행 횟수)

### ✅ 완료 — 묶음 37: 조합 찾기 계산 방식 근본 교정 — 로스터 전멸(전쟁) 승률 → 매치업 단위 승률, 모드 A/B/C 재편

실제 룬 비교의 기준은 이미 사이트에 있던 `runDinoQuickCalc`(단일 유닛이 죽으면 즉시 풀피로

검증하고 대화용 아티팩트를 전면 재작성한 뒤(리서치 도구 단계, 이 저장소 코드와는 무관), 이 검증된
계산을 실제 사이트 조합 찾기 기능에도 반영하는 통합 작업을 이어감.

**1차 제안(거부됨) — 조합 찾기 엔진을 통째로 `quickCalc`로 교체.** `quickCalc`는 count를 1로
고정하므로 인원수 조건부 룬(협동 공격=아군 4마리 이상, 고독한 분노=아군 1마리일 때)이 항상
잘못된 쪽으로만 발동함(코드상 반드시 "혼자"인 상태가 되므로 협동 공격은 절대 못 켜지고 고독한
분노는 항상 켜짐) - 사용자가 "보호막이나 고독한 분노 이런거 사용하는 사람들은 어떡해?"라고
지적하며 거부. 대안으로 "3번째 모드로 넣을까"까지 제안했으나, 최종적으로는 **로스터 방식
엔진(`runDinoBattleSimulation`) 자체는 유지하되 공룡 수를 실제 로스터(9~13마리)가 아니라
인위적으로 크게 잡고, 순위 기준을 "로스터 전멸 승률"이 아니라 "매치업(개별 듀얼) 단위 승률"로
바꾸는 방향**을 사용자가 직접 확정함(정확한 지시: "기존의 로스터 방식이 아니라 공룡수를 많이
하는걸로 다른 모드도 바꾸긴 해야 해. 근데 모드 A, B, C로 해두고... A: 가지고 있는 모든 룬을
대상으로 라운드로빈을 돌립니다. B: 메리트가 떨어지는 룬들을 제외하고 라운드로빈을 돌립니다.
C: 상대를 지정하여 조합을 찾습니다."). 이 방식은 `runDinoBattleSimulation`을 그대로 쓰므로
협동 공격/고독한 분노/보호막/희생 전부 실제 로스터 규모에서 정상 발동하면서, 공룡 수를 늘려
표본을 키운 만큼 매치업 승률은 통계적으로 안정된 값이 나옴 - 왜 "로스터 전멸 승률"이 아니라
"매치업 승률"이어야 하는지는 다음 문단.

**왜 로스터 전멸 승률이 아니라 매치업 승률인가.** 로스터가 소진될 때까지 이어지는 "전쟁" 승률은
공룡 수(dinoCount)를 키울수록 도박꾼의 파산 문제처럼 한쪽으로 급격히 수렴함 - 개별 매치업
승률이 51%인 근소한 우위라도 로스터가 수백 마리면 전쟁 승률은 사실상 100%/0%로 벌어져서, 그
근소한 차이 자체를 더는 구별할 수 없게 됨(변별력 소실). 반대로 매치업(1:1 듀얼) 단위 승률은
공룡 수를 아무리 키워도 그 자체의 확률로 안정적으로 남아있어서 룬 조합 간의 실제 우열을 계속
구별할 수 있음 - 그래서 "공룡 수는 크게(표본을 늘려 통계 노이즈를 줄이는 용도), 순위는 매치업
승률로(변별력을 유지하는 용도)"라는, 얼핏 모순돼 보이지만 실제로는 서로 다른 목적의 두 손잡이를
분리한 설계.

**엔진 버그 2건 발견/수정(`js/core/simulation-dino-battle.js`).** 공룡 수를 100 단위로 실측
벤치마킹하다가 발견:
- `aliveDinos(side)`가 매번 `side.dinos.filter(...)`로 다시 필터링하고 있었는데, 이 파일 안의
  모든 호출부가 이미 "죽은 개체를 `processFrontDeath`에서 즉시 splice로 제거한 뒤"에만 이
  함수를 부르므로 배열 자체가 항상 생존 개체만 담고 있었음(필터링이 원천적으로 불필요) - 로스터가
  큰 라운드로빈에서 턴마다 여러 번 호출되며 체감될 만큼 느려지는 게 확인돼서 `return side.dinos`로
  단순화.
- `MAX_TURNS = 3000`(공룡 5~13마리 규모만 염두에 두고 잡아뒀던 고정값)이 dinoCount≥200부터
  전투가 끝나기 전에 상한에 걸려 억지로 "무승부"를 반환하는 버그를 유발 - `Math.max(3000,
  (my.count + opp.count) * 200)`로 로스터 규모에 비례하도록 수정.
- Playwright로 dinoCount 2000까지 실측 검증(441~518ms, 실제 턴 수로 정상 종료, 더는 가짜
  무승부 없음). 5000~30000 구간에서 `Array.splice(0,1)`(배열 앞에서 제거, O(N))이 누적되며
  느려지는 별도의 O(N²) 이슈를 추가로 발견했으나, 이번 기능에서 실제 쓰는 규모(수백)에서는 영향이
  1% 미만이라 사용자가 범위 밖으로 확정("1% 미만이라면 충분하다") - 손대지 않음.

**모드 A/B/C 재편(`js/pages/dino-battle-page.js`).** 기존 "모드 A(일반 튜닝)/모드 B(상대 맞춤)"

  교체).

  "메리트가 떨어지는 룬을 제외"라는 사용자 지시를 등급 필터로 구현. 후보가 0개면 전용 안내

**수정 1.** 1단계에서 이미 계산되던 "확정형 방어 안전망" 지표(`deterministicExpectedDeathCount` -
확률형 효과가 전부 한 번도 안 터진다는 최악의 가정 하에 기대 사망 횟수, 지금까진 `byDeterministicSafety`로
후보군을 넓히는 데만 쓰이고 최종 승자 선정엔 안 쓰였음)를 `candidates`→`refined`→`preResolved`→
`verified` 전 구간에 그대로 실어 나른 뒤(추가 계산 없음, 이미 있는 순수함수 값 복사만), `bestSurvival`
reduce에 `avgDeadCount` 동률 시 이 값으로 먼저 한 번 더 가르는 단계를 추가(`b.deterministicExpectedDeathCount
< a.deterministicExpectedDeathCount`)하고 그래도 동률이면 기존처럼 dps로 결정. 이러면 실측상
구분이 안 될 때 룬 카탈로그 정렬 순서가 아니라 "확률에 하나도 안 기대도 더 잘 버티는 쪽"이 이김.

**원인 2 + 수정 2(대미지/균형 실측 기반 교체, 이번 세션 앞서 다룬 "최대 대미지" 요청과 동일 맥락).**
"최대 대미지"(`bestDpsEntry`)/"균형"(`bestBalance`)은 죽음·재소환·이동시간 개념 자체가 없는
`getTitanCombatMetrics()`의 정적 `dps`를 1단계에서 계산한 뒤 최종 승자 선정까지 한 번도 다시
계산하지 않고 그대로 썼음(반면 "최대 생존"은 실측 `avgDeadCount` 기반). `simulation-titan.js`에
`firstDeathTick`과 같은 패턴으로 `titanDefeatedTick`(타이탄이 죽은 틱, 안 죽었으면 null)을
추가하고, `avgFightDurationSec`(타이탄이 죽었으면 그 시점까지, 안 죽었으면 제한 시간 전체 - 세션
전체를 누적한 `avgTimeSec`와 달리 이번에 새로 추가한 값)를 반환값에 추가. `realDpsOf(r) =
r.avgTotalDmg / r.avgFightDurationSec`를 만들어 "최대 대미지"(`verified.reduce`로 실측 기준
재선정, 예전처럼 1단계 정적 1위를 그냥 다시 찾아오지 않음)와 "균형"의 대미지 축 정규화 모두에
사용, 화면에 뜨는 "예상 초당 대미지" 표시도 이 값으로 통일(예전엔 `avgTotalDmg/avgTimeSec`를 써서
분모가 "공룡이 처음 죽기까지 걸린 시간"이라는 엉뚱한 값이었음). 1·2단계 스크리닝(정적 dps 기반
`screened`/`byDps`/`candidates`/`refined`)은 손대지 않음 - 전체 조합에 매번 500회 시뮬레이션을
돌릴 수는 없어 "싸게 거르고 비싸게 검증"하는 기존 패턴 유지, 최종 승자를 정하는 지점만 이미
계산되어 있는 실측값으로 교체하는 최소 변경.

이번 균형 점수 공식(`TITAN_BALANCE_DPS_WEIGHT=0.7`) 자체나 "균형"에 힐이 뽑히는 현상(묶음21에서
이미 의도적으로 튜닝된 결과)은 사용자 확정으로 범위 밖 - 대미지 축이 실측으로 바뀌면 균형 결과도
달라질 수 있으니 필요하면 나중에 재튜닝.

**검증.** Node 재현 스크립트로 실제 리포트 시나리오(단단한피부1/피해저항1 둘 다 31레벨) 재실행 -

공격력, HP만 다르게 해서 한쪽은 자주 죽게 설정) - 정적 dps는 완전히 같아도(공격력이 같으므로)
실측 `realDps`는 자주 죽는 쪽이 확연히 낮게 나옴(946.8 vs 4330.6) 확인. 킬 속도 반영도 확인 -
타이탄을 90분 안에 잡는 조합과 못 잡는 조합을 비교하니 `avgTotalDmg`만으로는 둘 다 타이탄 최대

### ✅ 완료 — 묶음 40: 타이탄 조합 찾기 3개 슬롯 선정 기준 재확정(생존 타이브레이크 순서, 세 슬롯 각각의 역할 재확인)

묶음39에서 "최대 생존" 동률 타이브레이크에 `expectedDeathCount`를 추가했는데, 사용자가 실제 스탯으로

**1) "최대 생존" 타이브레이크 순서 정정.** 사용자가 예시로 지적: 지금 추천이 "강타 없이
흡혈+단단한피부1+단단한피부2+피해저항2+힐"(공격 기여 룬이 하나도 없음)인데, "강타"까지 넣은

확정: **"사망수가 0으로 동률이면, 그 다음은 딜(dps)이 우선"** - 묶음39에서 `expectedDeathCount`를
`dps`보다 먼저 비교하게 만들었던 순서를 되돌려, `dps`를 먼저 비교하고 `dps`까지 완전히 같을 때만
(예: 공격 기여가 0인 순수 방어 룬끼리의 1:1 교체 - 애초에 이 순서 문제가 발견됐던 단단한피부1

노이즈 없는 정적 `dps`가 실측 `realDps`와 사실상 같은 값이라 그대로 써도 안전함.

**2) "최대 대미지"는 이미 사용자 의도와 일치함을 확인.** "다른거 다 필요 없고 대미지만 제일 잘
나오면 된다"는 확인을 받음 - 다만 그 결과에 흡혈/단단한 피부 2 같은 방어형 룬이 섞여 나오는 걸

하라"고 했다가, 최종적으로는 "균형은 최대 대미지와 비슷하되 공룡을 덜 죽이는 쪽으로 가야 한다"로
정리 - 이는 이미 구현돼 있던 `titanBalanceScore`(realDps 정규화 + survivalQuality, 0.7/0.3 가중

**보유 룬 데이터 정정 + 후보군 실측 검증.** 사용자가 "빠른 계산"(같은 `runTitanSimulation` 엔진,

**2) 결과 상세화.** 이미 `runTitanSimulation` 결과에 있었지만 조합 찾기 카드엔 안 보여주던

`verified` 파이프라인에 실어 나르도록 추가(추가 계산 없음, 이미 계산되는 값을 그대로 노출)하고
카드에 새 타일로 추가.

**3) "빠른 계산"과 라벨 문구 통일.** 조합 찾기 카드가 자체 라벨(`titan.optimize.avgDeathTimeLabel`
"평균 사망 시간", `avgDeathCountLabel`+`avgDeathCountValue` "평균 사망 수"+"평균 {count}회",
`totalDmgLabel` "평균 대미지 합계")을 따로 쓰고 있었는데, 이게 "빠른 계산" 리포트가 이미 쓰던
같은 지표(`titan.quick.report.avgSurvivalTime` "평균 생존 시간", `avgDeadCount` "평균 공룡
사망 수"+`titan.live.deadCountValue` "{count}마리", `totalDmg` "총 입힌 피해량")와 완전히
같은 값인데 문구만 달랐음(예: "사망 시간" vs "생존 시간"). 조합 찾기 쪽 라벨을 빠른 계산 쪽으로
통일하고, 이제 안 쓰는 조합 찾기 전용 키 5개(`bestBalanceTitle`/`avgDeathTimeLabel`/
`avgDeathCountLabel`/`avgDeathCountValue`/`totalDmgLabel`)는 5개 언어 전부에서 제거. "예상
초당 대미지"는 빠른 계산엔 없는 조합 찾기 전용 지표라 그대로 둠.

**검증.** Playwright E2E - 결과 카드가 정확히 2개("최대 생존 조합"/"최대 대미지 조합")만 렌더링,
각 카드에 총 입힌 피해량/예상 초당 대미지/남은 타이탄 체력/평균 생존 시간/평균 사망 수/평균 생존
체력까지 6개 지표가 빠른 계산과 동일한 라벨로 표시됨, 위쪽 설명 문구도 2개 모드만 안내하도록
바뀜, 콘솔 에러 0건 확인.

### ✅ 완료 — 묶음 42: 사이드 메뉴 열었을 때 배경 스크롤바가 화면 크기에 따라 나타나던 버그 수정

`css/base.css`) 이 현상이 재현된다는 점에서 확인해보니, `toggleMenu()`(`js/ui/settings-ui.js`)가
사이드 메뉴(`.side-menu`, `position:fixed`)와 오버레이(`.menu-overlay`)만 띄우고 **배경 페이지
자체의 스크롤은 전혀 잠그지 않고 있었음** - 메뉴가 열려 있어도 배경 콘텐츠는 여전히 스크롤 가능한
상태로 남아있어서, 오버레이 너머로 휠/터치 스크롤을 하면(특히 모바일에서 스크롤 인디케이터가 잠깐

`document.body.style.overflow`를 "hidden"/""(원래 CSS의 overflow-x:hidden으로 복귀)로 토글하는
잠금을 추가해서 메뉴가 열려있는 동안 배경 스크롤 자체를 막음.

**검증.** Playwright로 (1) 메뉴 연 상태에서 마우스 휠을 크게 굴려도 `scrollY`가 전혀 안 움직이는 것
(2) 메뉴 닫으면 다시 정상적으로 스크롤되는 것 (3) 콘솔 에러 없는 것까지 확인.

사용자가 "심각한거 먼저 고치자"고 확정해 그중 게임 계산 정확도에 직접 영향을 주는 버그와 사이트가
깨질 수 있는 버그부터 아래와 같이 수정함.

**1) 공룡 대전 - `tribeControl` 문자열 불일치로 부족의 축복 1/2가 실전투에서 항상 무효였던 버그
(가장 심각).** `dino-battle-page.js`(설정 UI/저장소)는 `tileCfg.tribeControl`을 `"none"/"mine"/
"opponent"` 문자열로 저장하는데, `simulation-dino-battle.js`의 `computeSideCombatValues`는 이를
엔진 내부 진영 키인 `"my"/"opp"`와 직접 비교(`tileCfg.tribeControl !== side.key`)하고 있었음 -
이 두 값 집합은 절대 같아질 수 없는 서로 다른 문자열이라, 부족의 축복 1/2 룬이 실제 전투 시뮬레이션에서
구현 이후 단 한 번도 발동한 적이 없었던 것으로 확인됨(타이탄/더미/건물 페이지는 이 룬을 아예 룬
후보에서 제외하는 페이지라 이 버그의 영향을 안 받음). `tribeControlMatchesSide(tribeControl, key)`
헬퍼를 새로 추가해 `"mine"`↔`"my"`, `"opponent"`↔`"opp"` 매핑을 명시적으로 처리하고
`computeSideCombatValues`의 기존 비교를 이걸로 교체. Playwright로 직접 검증 - 타일을 내 진영이
차지한 경우와 상대/무소유인 경우의 실측 공격력이 이제 정확히 갈라짐(1020 vs 1000) 확인.

**2) 공룡 대전 - 흡혈(`computeVampBaseAtk`) 계산에 공격 타워 보너스/타일 조건부 룬이 누락돼 있던
버그.** 흡혈 기여도를 계산하는 별도 경로(`vampBaseAtk`, 협동공격 등 카운트/타일 조건부 룬은 제외하는

축복처럼 타일 조건이 걸린 룬도 무조건 걸러내고 있었음(제외 목적이 "카운트/타일 조건부라서"가 아니라

대상이 아니었음). `computeVampBaseAtk`에 `tileCfg`/`key` 파라미터를 추가해
`computeSideCombatValues`와 똑같은 방식으로 타워 보너스를 더하고 위 1번 헬퍼로 타일 조건을 게이팅하도록
수정. `simulation-arena.js`의 대응 함수(`buildArenaSideRunes`/`buildArenaSide`)도 일관성을 위해
같은 파라미터를 추가(아레나는 이 두 룬이 애초에 `ARENA_UNSUITABLE_RUNE_LIST`라 실질적 영향은 없음 -
공룡 대전에만 실제 영향).

**3) 공룡 대전 - 광역기(메테오/가시)에 죽은 비전방 공룡이 "좀비"로 남아 다음 턴에도 계속 공격하던
버그.** 같은 타일/광역 피해로 전방이 아닌 예비 공룡의 체력이 0이 됐을 때, 기존 코드는 전방 사망
처리(`processFrontDeath` - 죽음 통계 집계, 새 전방 소환, 관련 룬 재계산 등)를 전방 공룡 사망 시에만
호출해서 이 "부수 사망"은 아예 처리되지 않고 배열에서 빠지지도 않은 채 남아있었음 - 이후 턴에 0
HP인 채로 여전히 "공격"에 참여할 수 있는 좀비 유닛 버그. `nonFrontAoeDeaths` 배열을 새로 도입해 4개
광역 피해 분기(메테오/가시 × 같은 타일/광역) 모두에서 새로 0 HP가 된 비전방 공룡을 여기 담고, 턴
끝에 `processFrontDeath(d, ..., false)`(전방 사망이 아님을 표시하는 신규 4번째 인자 `isFrontDeath`
추가 - 전방 소환 이벤트가 잘못 안 뜨게)로 일괄 처리하도록 수정. **구현 중 자체 발견한 버그**: 처음엔
이 배열 선언을 `processFrontDeath` 함수 정의 "다음"에 뒀는데, 같은 턴 안에서 그보다 먼저 실행되는
룬 처리 블록이 이 배열에 push해야 해서 `const`의 일시적 사각지대로 인해 `ReferenceError`가 날 뻔함 -
테스트 실행 전에 코드 구조를 다시 읽다가 스스로 발견해 선언을 턴 최상단(`event` 객체 생성 직후)으로
옮겨 수정. 200회 연속 시뮬레이션으로 좀비 유닛이 전혀 안 남는지 재확인.

**4) 공룡 대전 - 죽을 준비(반격) 한 방에 공격자가 죽었을 때도 좀비로 남던 버그, 양쪽 동시 사망

전혀 호출하지 않고 있었음 - JS 가비지 컬렉션만으로는 GPU 메모리가 해제되지 않아, 씬을 반복
재생성하는 페이지(타이탄/공룡 대전/건물/더미, 페이지 이동·설정 변경마다 재생성)에서 방문할수록
GPU 메모리가 계속 쌓이는 누수였음. `rebakeColors`/`dispose` 양쪽에 텍스처·머티리얼 dispose 호출을

재생성 함수가 기존 씬 변수를 덮어쓰기 전에 `.dispose()`를 먼저 호출하도록 수정(타이탄 페이지는
씬 변수가 함수 지역 변수라 매 방문마다 리셋돼 dispose가 무의미했던 부분도 모듈 전역으로 끌어올림).
몽키패치로 dispose 호출 횟수를 세는 Playwright 테스트로 검증.

파일 요청을 전부 404로 강제하는 Playwright 테스트로 나머지 부트 시퀀스(메뉴 열기 등)가 정상 동작함을

해시는 `renderHome`으로 대체 렌더링되는데, `body.dataset.page`엔 실제로 그려진 라우트가 아니라
